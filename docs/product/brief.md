# Product brief — personal agent workspace

> Historical baseline. Current direction: [Product vision](vision.md). Workspaces are persistent chats; memory is automatic; the app is dark and chat-first. Conflicting earlier decisions are superseded.

Status: delegated foundation shared understanding confirmed after rounds 1–3; application implementation gates remain open. The founder's relayed custom-UI direction supersedes catalog-only scope.
Date: 2026-09-09.
Working title: **Personal agent workspace**. This is descriptive, not a cleared public brand.

## Authority and evidence

The founder delegates reversible scope, interaction priorities, and acceptance criteria to the project-local product owner. That delegation is not human consent for account access, spending, signing, publication, destructive actions, license changes, or secret sharing.

The inherited founder direction is an open-source, local-first Hermes workspace: conversations produce durable dashboards over explicitly connected accounts; macOS and Windows without Electron; BYO model providers, including a custom OpenAI-compatible endpoint; multiple devices and Orca interoperability eventually; optional hosted subscriptions later. The coordinator subsequently relayed the founder's explicit instruction to include genuine model-authored custom UI guided by a design system, not only preset rearrangement. That product direction is recorded in [ADR 0001](../adr/0001-generated-ui-is-a-product-capability-not-host-authority.md); it does not authorize account access or privileged execution.

Everything labeled a target or default below is a product-owner decision, not an observed result. No customer research, working integration, platform-performance measurement, security review, or runtime QA pass has yet been established. See [the decision record](grill.md) for provenance, alternatives, factual blockers, and the remaining design frontier. [CONTEXT.md](../../CONTEXT.md) is the canonical glossary; use Workspace, Connection, Run, Device, Data snapshot, Dashboard revision, and Capability grant rather than competing domain terms.

## Operator and job

Primary operator hypothesis: an individual power operator managing a busy personal workflow, not a team administrator.

Job: **Show me which recent emails deserve attention, explain why, and preserve that view so I can return without rebuilding it.**

The first truthful connected slice is one explicitly authorized Gmail connection, bounded read-only retrieval, a conversation-generated triage dashboard, save, cold restart/reopen, and explicit refresh. Findings show source links, retrieval scope, freshness, and uncertainty. A triage suggestion is not a claim that an email is objectively urgent, and must not invent facts missing from the authorized headers or snippets.

Reject a connector marketplace, chat-only summaries, and team workflows as initial deliverables. Gmail is a narrow value hypothesis, not a validated market conclusion.

## Delivery stages

1. **Foundation:** local agent definitions, product/domain/architecture decisions, evidence-backed integration findings, and a dependency-ordered Beads backlog. Local agent and operational files do not belong in product commits.
2. **Fixture interaction prototype:** a real Tauri client using synthetic mail. Include both trusted-catalog rendering and genuine model-authored custom React/TypeScript preview → conversational revise → explicit save → cold restart/reopen → rollback. Generated code runs only in a contained runtime, never the privileged host. A recorded generated artifact may test playback, but only an actual generation/revision run through the permitted gateway counts as the authored-UI demonstration. Label synthetic data and any simulated steps throughout. No live Gmail or paid endpoint required. This tests interaction, recovery, and authored-UI capability, not account integration or product demand.
3. **Authorized connected pilot:** real, narrowly granted Gmail retrieval and a permitted, operator-selected model endpoint through a verified Hermes integration. Requires actual operator consent, safe credential storage, enforced grants, retention/egress controls, independent review, and target-platform runtime receipts. Trusted-catalog and live custom-UI readiness are separate evidence gates: no live data reaches custom code until the isolation/resource/bridge/egress spike passes. A catalog-only connected preview must say live custom UI is still blocked, not quietly redefine the founder's capability away.

The PO confirms shared understanding for the **foundation plan only**: settled product choices plus explicit technical/legal/authorization gates form an actionable plan. This is not a completed app, passed spike, final architecture, runtime QA verdict, or human authorization. Hermes adapter compatibility, custom runtime isolation, Gmail compliance, and Orca interoperability remain evidence-gated implementation branches.

## Desktop and generated UI

- Selected direction: Tauri v2 with React/TypeScript, subject to capability, packaging, and platform feasibility evidence. No Electron; native dual apps rejected for the initial implementation cost, not ruled out forever.
- **Trusted catalog mode:** bounded stack/grid layout, metric, message list, table, and plain text; validated versioned declarative specifications only in the privileged renderer. Initial proposed caps: three layout levels, twelve content components, four grid columns. Host pagination/scrolling bounds visible rows to the granted snapshot. No charts required for the Gmail slice.
- **Custom authored mode:** genuine generated React/TypeScript presentation code guided by supplied design tokens/components, using a pinned host-supplied dependency bundle. It is not limited to rearranging catalog entries. Custom layouts and presentation logic are allowed only in an isolated runtime with preview/revise/save/rollback. No arbitrary package install/import, remote scripts/assets, credentials, native IPC, ambient network, connector authority, or device enrollment.
- Bindings and actions are host-owned, typed, and scoped to workspace, connection, run, revision, snapshot and current grant. The bridge delivers only approved bounded projections and validates origin/session identity, message schema, size, rate, correlation and current authorization. Renderer messages cannot manufacture trusted operator intent. Refresh and source navigation require a real host-owned operator control/confirmation, not just a custom-code claim of a click. Source URLs are host-validated. Rendering alone never triggers a connector call.
- Isolation is **unsolved until tested**. An iframe/CSP alone is not proof. A spike must select and adversarially test origin separation, bridge spoofing/replay, every egress class, native-command denial, dependency/compilation containment, CPU/memory limits, watchdog termination and host recovery on macOS and Windows. Even fixture code needs baseline host/resource containment; synthetic data does not make arbitrary code safe. No live-data custom UI before a passing spike and independent review.
- Operators own saved source/specifications and revisions within the workspace. Each immutable revision records mode, source/spec hash, schema/compiler/runtime/design-system versions and parent revision; no secrets. Preview is isolated; saving is explicit; repair proposes a new preview, never silently changes the saved surface. Failed generation, validation, compilation or execution preserves the last working revision. Rollback restores code/layout, never resurrects expired snapshots or revoked grants. Runtime incompatibility preserves the old artifact and asks for a repair preview rather than executing blindly.
- Email-derived text is bound to expiring snapshots, not deliberately embedded in generated source or durable layout. Use schema/synthetic examples for UI-code generation where possible. Any source, bundle, label, summary or conversation containing account-derived content is sensitive and must expire/purge with its connection; this requires evidence, not an assumption that code is data-free. Revocation terminates custom runtimes and prevents further bridge delivery; already disclosed data cannot be retroactively undisclosed.
- Dashboard revisions version presentation/bindings independently from data snapshots. Save and refresh publish atomically only after validation; interruption or invalid generation retains last-valid state. Version incompatibility is explicit, never silently overwritten. A trusted host owns preview/save/repair/rollback controls even when custom content fails.
- Local SQLite is the intended durable store for the connected pilot, pending the storage/security ADR. A fixture-only atomic file store may validate the contract first, but does not prove SQLite migration, encryption, or real-account durability.

## Retrieval, privacy, and control defaults

These are proposed product limits, not Gmail API limitations.

| Concern | Initial connected-pilot policy |
| --- | --- |
| Scope | One Gmail connection; INBOX messages received within a rolling seven-day window; newest 100 messages maximum. Exclude spam/trash. Display the exact scope, count, truncation, and partial-fetch status. |
| Content | Initial baseline: minimum needed message identity/link, sender, subject, received time, and relevant state/labels available through verified metadata operations. No snippets until their exact scope/response contract, permitted use, and operator consent are established; never assume `gmail.metadata` permits them. No full bodies, attachments, raw MIME, or remote images. Snippets contain body excerpts and require explicit disclosure if later enabled. |
| Wider access | Older/larger searches, other folders, bodies, and attachments are not automatic fallbacks. They require a separate bounded grant and design gate; their UI is outside the first pilot. |
| Refresh | Explicit operator request only, including initial retrieval. At most one active retrieval/generation pipeline per connection. Duplicate refresh does not launch another pipeline; no schedule, startup read, or reconnect read. |
| Retention | Keep only the last successful bounded snapshot plus short-lived in-flight staging. Snapshot and email-derived summaries/conversation content expire seven days after retrieval; freshness is not extended by local viewing. Purge staging on completion/failure/cancellation. |
| Expiry | Check before display, prompt assembly, export, and run publication. Purge expired content at next launch before access and while the app is open. An app that is not running cannot promise wall-clock physical deletion. |
| History | Retain minimal content-free run audit metadata for 30 days. Saved dashboard definitions persist until operator deletion; expiry leaves a visible no-data state without rebuilding the layout. |
| Revocation | Immediately invalidate the grant, cancel best-effort, reject later results from that grant even if they arrive successfully, and purge associated cached account content and sensitive derivatives. Preserve only content-free definitions and audit metadata. |
| Egress | Before model processing, disclose and obtain consent for the selected endpoint and account-data categories sent there. Local-first does not mean no egress. Already transmitted data cannot be recalled; disclose external retention separately. |

The coordinator supplied verified evidence from [Google's Gmail scope documentation](https://developers.google.com/workspace/gmail/api/auth/scopes): both `gmail.metadata` and `gmail.readonly` are **Restricted**; metadata covers headers/labels, not bodies, and body access needs readonly. Inbox/date/count application bounds do not narrow the OAuth grant. The page states that storing restricted-scope data on servers or transmitting it requires a security assessment; it establishes no desktop/BYO exemption. OAuth verification, Limited Use, and security-assessment applicability are connected-pilot/release gates, especially for sending email data to a model provider. BYO OAuth credentials do not bypass these rules. Do not enable real-account retrieval or egress until the intended use has an evidenced compliant path and operator consent.

The bounded listing strategy must be verified under the selected scope; do not assume Gmail search parameters are available with metadata-only authorization. If a seven-day bound cannot be implemented efficiently and truthfully under that scope, keep the connected stage blocked and revisit scope with evidence rather than silently fetch the mailbox. Credential revocation at the external service and local grant revocation are distinct; stop local use immediately even if provider-side revocation fails, and report that failure.

Credentials stay with their device by default, in OS-supported secure storage rather than dashboard files, prompts, logs, or exports. Secrets are never synchronized automatically. Operators can delete local cached content and export a portable secret-free workspace; deletion semantics must disclose backups and storage limitations rather than promise forensic erasure.

## Model providers and authentication

First support a deliberately configured OpenAI-compatible endpoint and BYO key. Compatibility must be tested, not assumed from the URL or marketing label. No mandatory hosted product account.

**Direct Claude.ai / Anthropic subscription OAuth is unsupported and blocked absent separate explicit authorization from Anthropic.** The coordinator supplied verified evidence from [Anthropic's authentication and credential-use policy](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use): third-party developers may not offer Claude.ai login in their applications or collect, store, or intermediate Claude.ai session tokens. Signing into an unmodified Claude Code binary does not authorize token reuse in Hermes. No token import, proxying, harvesting, or suggestion that a subscription supplies API access.

API keys or supported cloud-provider authentication are the lawful direction, subject to their terms and compatibility. Other providers' official OAuth remains gated on their independently verified policies. Gmail connector OAuth is a separate integration question. Product BYO support authorizes neither account access nor spending; agent development may use only the permitted local gateway and may not activate paid providers.

## Workspace and remote boundary

MVP has one device-local workspace and no hosted product identity, team account, synchronization, discovery, or pairing. Runs carry workspace, applicable connection, executor device, and dashboard revision identity from the start. A device identity does not itself grant trust or access.

One explicitly configured remote Hermes connection is the first intended remote capability, but **remote execution remains blocked pending tested authenticated transport, effective authorization, cancellation/reconnect, and credential-boundary evidence**. It is not an available feature merely because upstream exposes APIs. No credential forwarding, automatic enrollment, or trust based on model/imported content. Remote execution and multi-client synchronization are different features.

### Hermes execution and event contract

Coordinator-supplied research pins Hermes to `fd6434b3b36592367ac5faa180b905d64e29214c`, MIT, v0.21.1, Python >=3.11,<3.14. Real HTTP Runs/session APIs, ACP stdio, and TUI JSON-RPC/WebSocket exist. Upstream recommends TUI for full desktop parity; the bounded MVP does not promise parity. HTTP bearer access is powerful; tools execute on the server (`split_runtime=false`). MCP's default full trust and `readOnlyHint` are not enforceable safety boundaries. Custom provider `base_url`/`api_key` are supported. Native Windows is documented, not runtime-verified; the embedded POSIX PTY chat pane is excepted. Bounded research found no Orca source/API and no local Mac Hermes installation; that is not proof either does not exist elsewhere.

**PO selection, conditional on compatibility spike:** an owned control-plane adapter on the configured runtime host over Hermes HTTP Runs/session APIs. Do not expose Hermes bearer credentials or raw tool/session APIs to generated code. Server-side configuration/enforcement must actually deny out-of-grant tools; prompts, client filtering and read-only hints do not establish this. ACP is not remote device identity. Revisit the seam if the spike cannot enforce the bounded workflow; do not quietly adopt full-trust tooling to preserve the plan.

Upstream SSE uses one consumptive queue and offers no replay/fanout; disconnect drops the transport. Select one upstream adapter consumer per run and own durable product events, sequence/correlation IDs and status reconciliation. Envelope scope includes workspace, connection, executor device, run, revision, grant generation, and applicable snapshot; product identity is not an upstream session ID. Reconnect queries/reconciles status before allowing a new run and shows unknown/interrupted when proof is unavailable, not manufactured success. Idempotency and replay are product contracts to spike, not asserted upstream features. Cancellation is not rollback of server work; invalidate delivery/publication locally, request cancellation, and reconcile the real terminal state. Future multi-device replay/fanout requires the adapter's demonstrated durable semantics, not multiple direct SSE subscribers. Approval identity is reserved and scoped separately from grants; consequential actions remain unavailable in MVP.

## Acceptance and release gates

All numbers below are proposed gates to validate, not measured facts.

- Fixture slice: complete conversation → trusted-catalog dashboard and genuinely authored custom React/TypeScript preview → conversational revision → explicit save → cold restart/reopen → rollback on synthetic data. Capture generation/revision receipts through the permitted gateway; distinguish actual generated artifacts from prerecorded playback. Visible fixture labeling throughout; generation/compile/runtime failure and interrupted save preserve last-valid state.
- Custom-runtime gates: synthetic adversarial attempts cover origin/bridge spoofing and replay, egress, native IPC, dependency escape, infinite loops, memory exhaustion, cancellation and host recovery on each OS. The spike sets finite enforced resource budgets; proposed recovery target is host-responsive termination within two seconds of a watchdog/limit violation. Do not use data sensitivity as the only reason to contain fixture code. Live data additionally requires proven scoped projection, operator consent enforced by the host, runtime termination when access expires or is revoked, and independent review. A blocked security gate is not removal of authored UI from product scope.
- Connected slice: the same path with real authorized data, source-grounded findings, visible scope/freshness/truncation, and runtime evidence of no Gmail mutations. No manual code/config editing to complete the normal operator flow.
- Trust/privacy: negative tests deny absent, expired, revoked, wrong-workspace/account/device grants; adversarial email/model/custom-code output cannot execute in the privileged host, expand scope, change endpoint, or obtain a capability. Custom presentation code may execute only within its proven contained runtime. Expiry and revocation cover cached content, staged results, generated summaries, tainted source/bundles, retained conversation content, and running renderers.
- Desktop: on each named target OS/hardware configuration, target cold-launch-to-interactive p95 <= 3 seconds over 20 launches and local filter/sort response p95 <= 100 ms over 100 interactions on a 100-message fixture. Target idle application process-tree memory <= 250 MiB after 60 seconds quiescent; record WebView accounting explicitly. Network/model latency is measured separately, not hidden in local interaction metrics.
- Accessibility: all catalog interactions usable by keyboard, accessible names present, status/error states not conveyed by color alone.
- Value hypothesis: at least three of five consenting target operators return on three separate days within a week and report a concrete triage benefit. This is a small formative pilot, not statistical market validation.
- Runtime evidence: actual macOS and Windows cold-launch/screenshots and measured behavior before claiming either platform is verified. A one-OS preview must say so. Backend runtime belongs on the configured runtime host. Static tests and CI do not substitute for runtime receipts.
- Delivery: SPIKE → IMPLEMENT → independent multi-lane REVIEW → runtime QA; loop on blockers. Do not call unavailable lanes passed. Draft PR/publication only with authorization; no signing, paid endpoint activation, public distribution, commit, or push is authorized by this product brief.

## Explicit roadmap exclusions

Full Gmail bodies/attachments and wider mailbox queries; scheduled monitors; connector writes or consequential actions; broad connector catalog; browser cookie/profile harvesting; shell/desktop automation; multiple local connected accounts in the first pilot; device pairing/discovery; multi-client synchronization/conflict resolution; hosted/team accounts; Orca adapter; SaaS billing; privileged or uncontained generated-code execution; arbitrary dependency installation; chart-catalog expansion; final brand/license/signing/distribution. **Contained custom authored UI is in scope and first-class, not a roadmap exclusion.**

Later dogfood milestone: view Beads issues and agent work through the app, with Orca communication only after its real source/API and security contract are verified. Begin read-only; any repository change requires explicit scoped approval. No auto-merge or self-modification of the trusted host. This is not a dependency of the synthetic authored-UI prototype.

The open-source direction is a requirement, but no license is yet selected or applied. Apache-2.0 is only the PO's proposal for compatibility/legal review and explicit authorized selection before distribution. A public brand requires separate clearance. See [next issues and open frontier](grill.md#testable-next-issues) for the dependency gates.
